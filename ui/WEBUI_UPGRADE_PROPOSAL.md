# WebUI 升级方案(草拟·供用户定板,未实现)

MasterUI 起草 · 范围/工作量(S≈半场, M≈1场, L≈多场)/风险,逐块列。**本文件只是方案,未改任何代码。**

---

## 1. 核心:morphdom 增量更新【全铺】

**现状**:morphdom 只用在【待办池】renderTodos(已验证:刷新中输入/下拉/打开的编辑器/光标天然不丢、卡片原地 patch 不闪)。其余面板仍 `innerHTML=` 整体重建 → 每次 poll(10s)/SSE 刷新整块 DOM 重建 → 闪、滚动位跳、正在交互的状态丢。改造模式已成熟(待办池就是样板):给列表项加稳定 `id` 作 key → `innerHTML=` 换 `morphdom(node, html, {getNodeKey, onBeforeElUpdated})` → 删该面板任何 bespoke 焦点/选择保护。

**逐面板评估**(按建议优先级):

| 面板 | 刷新源 | 现状痛点 | 改造 | 工作量 | 风险 |
|---|---|---|---|---|---|
| 舰队总览表 `#fleetBody` + 可展开任务明细行 + 全局 send/reply 两个 `<select>` | render()(SSE+10s poll,高频) | 最常盯、刷新最勤 → 闪最明显;展开的任务明细行/下拉选择每次刷新被重建 | 行加 `id=fleetrow-<role>`;明细行 `id=det-<role>` 保展开态;两个 select 已手动保 value,morph 后天然保 | **M** | 中:明细展开态要靠 key 保;最高收益面板,先做 |
| BI 任务消耗表 / 在岗资源表 / 活动历史 / KPIs / 在跑 | loadBI()(10s 独立) | 纯只读 → 仅闪,无输入丢失 | 行加 `id`,直接 morph | **S**(每张) | 低(无输入) |
| 派工效率 `#dmRoles/#dmKind/#dmTop` | loadDispatch | 只读,闪 | 同上 | **S** | 低 |
| 可恢复会话 `#sessBox` | loadSessions(60s+按需) | 只读列表,闪 | 行加 `id=sess-<id>`;"显示全部"勾选在列表外不受影响 | **S** | 低 |
| 历史用量 `#uProj`/图表/legend | loadUsage(按需+进tab) | 含 canvas/SVG 图表 | **图表不 morph**(本就重绘),只 morph 周边表格/legend | **M** | 中:canvas 别交给 morphdom,分开处理 |
| 实时 live.log `#liveBox` | 选 role 后轮询 | 已是 `<pre>.textContent` 追加,非结构化重建 | 不需 morphdom,只需【保滚动位】(贴底时跟随、否则不跳) | **S** | 低 |

**全铺总工作量:M**(模式已验证,逐面板多为机械套用)。**主要坑**:① canvas 图表别 morph;② 任何【命令式注入】的子树(像当初 note 编辑器)要先改成 state 驱动再 morph,否则被刷掉;③ key 必须稳定唯一(用业务 id,不用数组下标),否则增删项匹配错位。

**收益**:全站不闪、滚动/展开/输入态天然保留 → 真 app 观感。**建议**:做,按上表优先级分阶段(①舰队 → ②BI/派工/会话/活动 → ③用量表格;live.log 只补滚动位)。不阻断现用,可一面板一上。

## 2. 一致性梳理

**现状**:这轮加了很多 —— 顶栏(连接/在跑claude·在岗/🙋待确认/🩺健康)、待办回路回复框、BI 双表、在岗vs daemon 区分、历史用量(账单级图表)、可恢复会话。其中 **BI tab 已严重过载**:运营消耗(metrics)+ 在岗进程资源(psutil)+ 历史用量账单 BI + 派工效率 + 活动历史,五块挤一个 tab,口径还不同(实时 vs 账单 vs 进程)。

**建议**:

| 项 | 建议 | 工作量 | 风险 |
|---|---|---|---|
| BI tab 过载 | 把【历史用量】(token_stats 账单级、全量成本、图表)拆成独立 tab,与【运营/资源】(实时 daemon 消耗 + 进程占用)分开 —— 两者受众/口径不同(全量账单 vs 仅自动化派工≈0.5%) | **S**(tab 重分配) | 低 |
| 0值/空折叠口径 | 统一一条规则"0/空 → 折叠或置底,不占主视野"(BI 消耗表刚做了;同样套到 fleet 未声明计数、派工 top-N、活动历史) | **S** | 低 |
| 刷新节奏不一 | 现 loadBI 每 10s 无视 tab 是否可见都刷(白耗 psutil 子进程扫 + token)。建议【只刷当前可见 tab 的重面板】(tab 切换时才拉),health/fleet 这类顶栏全局态保持低频后台。 | **S-M** | 低,且省成本/CPU |
| 顶栏徽标密度 | 暂可接受;若再加可考虑分组(状态类 / 计数类) | S | 低 |

**收益**:信息分层清晰、口径不混、刷新不浪费。**建议**:BI/历史用量拆 tab(S)+ 刷新按可见性门控(S-M)值得做;0值规则统一顺手做。

## 3.(可选)ab route 入 UI —— 派活"建议对口角色"

**现状**:`ab route`(按关键词在花名册 caps/desc 找最对口 role)只有 CLI。WebUI 派活/发任务时,用户从【所有 role 的平铺下拉】里自己选 → 曾因默认选中误派(GIT管理 那次)。

**建议**:派活弹框 / 发任务表单里,加"建议对口"提示:新增 `/api/route?q=<标题+详情>` 后端 shell `ab route`,把 top1-2 推荐 role 作为快捷 chip 显示在下拉上方,点击即选。

**工作量:M**(新端点 + 前端 chip)。**风险:低**。**价值**:减少误派(有过真实事故),但非阻塞性 —— **建议列为 phase-2 nicety**,morphdom 全铺 + 一致性梳理优先。

## 推荐排程(若用户全要)
1. **P0**:morphdom 全铺(先舰队,再只读各表)—— 体验主升级,M。
