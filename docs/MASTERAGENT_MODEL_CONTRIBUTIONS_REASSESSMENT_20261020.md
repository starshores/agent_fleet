# MasterAgent 模型贡献重新评估

日期：2026-10-20。本文修订[首轮分析](MASTERAGENT_MODEL_CONTRIBUTIONS_20261020.md)的评价与归因，保留原稿和原始数据作为基线。后续开源写作优先采用本次结论；材料仍只保存在本机。

**首轮的大部分历史事实成立，但贡献画像需要调整：Fable 的 UI 实现和既有系统平台化被遗漏或写窄；Opus 的一项代码实现归因需要撤回；Astra 的新架构交付与日常产品承接程度必须并列评价。** 更合适的分析单位是具体成果及其纠偏过程，而不是给每个模型固定一种能力标签。

配套[重评账本](history/model-contributions-20261020/reassessment.json)记录本次判断、代表案例、证据位置和原稿对应项。首轮的 454 条 Git 统计保持有效，仍不能用于贡献比例或能力排名。

## 成果与作者分别判断

一项代码改动可以确定存在，而具体实现模型仍然未知。本次分别保存两种证据：

| 评估对象 | 可以确认什么 | 不据此推导什么 |
| --- | --- | --- |
| 历史代码差异 | 功能、边界或判据发生了怎样的改变 | 每行代码由哪个模型生成、设计是否独占 |
| 提交协作署名 | 提交声明某模型参与 | 被提交内容全部出自该模型，或署名已认证实际推理身份 |
| 用户回忆与明确阶段文档 | 当时主要使用的模型和方向 | 阶段内每个角色、审阅者和集成者的模型 |
| 历史测试和验收记录 | 当时具体场景的检查结果 | 本轮已复现，或所有相关场景与生产负载均通过 |
| 发行包与摘要 | 内容已封存且可追溯 | 服务已切换、旧功能已迁入、实际用户收益已测量 |

每个案例同时记录提出、实现、复核、集成与纠偏的角色。角色身份和模型标签不互相替换；署名之外的分工线索优先保留，不让一条 trailer 抹掉多人劳动。

## 用具体案例重新看贡献

### Opus 的产品建设与 Sonnet 的行为修复

首个仓库快照已保存可运行的文件总线与控制台，后续 Opus 标签提交又收敛状态判据和存储引用。用户确认最初主要使用 Opus，因此“Opus 协助建立体系并持续演进”有支持；首提交本身仍不是所有早期组件的逐项作者证明。`6688c0a` 的状态单一来源和 `bcd13a0` 的引用契约，说明工程治理并非后期模型才引入。

7 月 20 日，`ce19133`、`278b7ec` 拆分后端与 HTTP 路由，提交声明 Opus 协作，并记录端点返回正常、SSE 能连接。7 月 28 日，Sonnet 标签的 `ab62d95` 修正了 SSE 对整数副本的读取：连接可以建立，但后续变更必须读取 `api._change_ver` 才能收到。该提交还增加 HTTP 来源校验和回执清理的路径限制。

这里同时成立的是模块化贡献与行为验收盲区。Sonnet 的价值在于补上运行正确性和写操作边界，不能因为提交数较少就将其视为装饰性工作。依据：上述代码差异及[工程清单](BUS_EXCELLENCE_PUNCHLIST.md)。

### Fable 也交付了跨前后端的产品改动

首轮没有纳入[UI 2.0 收口记录](UI_2.0_CLOSEOUT.md)，导致 Fable 的贡献过度集中在“审计和后端”。

- `b738176` 把展开态纳入状态驱动渲染，改善刷新后展开内容丢失。
- `c9e7c27` 补齐派工效率面板容器与接线。
- `f0cbb86` 抽出 CLI/UI 共用的 `route_scores()`，增加推荐接口和派活表单提示。
- `dc33cc0` 拆分页面装配，并记录拆分前后输出字节一致检查。

这些提交均声明 Fable 协作；收口文档记录 MasterAgent 主实施、Master数分逐阶段复核、MasterUI 保留运行维护。这里有跨前后端的实际产品交付，不只是审阅建议。

同一收口文档也明确：大量局部刷新和可见性控制在本轮之前已经存在。这批工作应记作剩余问题收口和新增交互，不能把整个旧 UI 的成熟度也归给 Fable。有些验证属于结构检查而非浏览器视觉复测，保持原有验收范围。

### 并发加固有价值，后续判据仍会出错

Fable 标签的 `03f913e`、`75190b9` 对领取锁、共享 JSON 更新、临时文件、崩溃窗口及任务匹配进行了实际加固。历史清单记录并发试验，但这只支持相应场景，不能证明可靠性从此完成。

9 月 24 日的纠偏链更能说明协作价值：`bd27d27` 用领取进程死亡判定孤儿；`1cbc8ed` 随后按Master数分反馈纠正，因为 wait 正常领取后本就退出，原判断可能把在办消息退回导致双处理。后者补入“正常领取后 wait 退出、turn 仍活跃”的场景。两个提交都声明 Fable 5.1 协作，也都记录 61/61。

因此应评价为“针对已发现问题持续加固，依赖复核纠正新增判断”，而非把 Fable 描述成只纠正别人、自己没有引入风险。相同测试数量不能证明相同覆盖，更不能由这个案例计算模型错误率。

### 前期平台化已有实作，3.0 扩展了不同边界

七月至九月的工作不仅是外迁文件：

- `26ec7cb`、`72e61f4` 建立业务注册及能力的外置与合并读取，缺业务表是合法空载。
- `ea72064` 用只读合并视图补充业务描述，写方继续使用原件，防止业务内容重新写回基建存储。
- `3d2f5d8` 将专用锁改为通用资源锁；`6067eae` 将操作提示变为角色配置输入。
- `8cc78f8` 至 `4807cbc` 迁出业务工具，并在消费方调整后删除转发桩。
- Opus 标签的 `1ffac70` 配合修改 UI 读方，去掉业务待办种子。

[分离交付记录](../fork_exchange/genesis_20260923_separation-biz-infra.md)保留了空载、有载文本一致、资源竞争和提示覆盖等验证。设计、实现、分类裁决、消费方切换由多角色共同推进。

更准确的继承关系是：**前期已在兼容运行条件下完成一轮平台化；Astra 主力阶段选择独立安装、部署绑定和事务协调的新实现路线，并验证限定范围的同构建换域。** 两阶段的范围不同，不能用后来选择的架构反推此前只是未成熟原型，也不能把前期检查扩写成完整业务隔离。

### 新机制会暴露既有组合问题，也会得到跨模型修复

Fable 标签的 `7ea8999` 增加等待注册表与宿主检查；后续 `f50507d` 明确借助此前统一的状态判据，让多个读方一起消费新机制。

增加心跳写入后，既有 UI watcher 对心跳文件的监听放大了刷新负担。用户反馈控制台卡顿，随后 Opus 标签的 `4dbf810` 排除心跳噪声并去抖。[问题记录](../fork_exchange/problems/webui-sse-heartbeat-firehose.md)明确区分已有 presence 心跳与新 wait 注册心跳，记录 MasterUI 实现、MasterAgent 复核；这不是把全部问题简单归给等待注册表。

这条链支持“架构整理—机制增加—使用反馈—跨角色修复”的累积过程。模型在不同任务中可以搭建、审阅、引入问题或修复问题，不宜固定成“Opus 只搭建、Fable 只纠错、Astra 只做架构”。

### Astra 的净增量与迁移收益分开评估

Astra 主力阶段有明确的实现成果，不能降格为只有规划：

| 成果 | 可核查的新增价值 | 尚不能计入的收益 |
| --- | --- | --- |
| 业务安装、启停与代次 | 不可变安装快照、部署绑定、旧身份撤销和在飞工作守卫 | 任意业务文件工具、网络或操作系统权限隔离 |
| 执行与恢复 | Task/Attempt、租约、迟到发布限制，不明执行先核对再决定是否重试 | 无需人工判断的普遍自动恢复、原生会话任意续接 |
| 3.0 纯文本执行 | 双角色持续接单、运行中补充、停止和断线恢复有真实原生验收记录 | 旧 fleet 已接管，或所有业务角色可直接替换 |
| 3.1 持久交接 | 来源映射与任务、结果与投递意图分别同事务，固定端点与回执核对 | 完整旧入口适配、真实业务交接、下游处理和用户已读 |
| 工作台与交付记录 | 公共命令、跨代历史、来源明确的运行事实、封存包及失败日志 | 完整旧 UI、真实 Claude/混合团队、已测量的生产稳定性提升 |

源码锚点包括 `service.py` 的 `install/activate/deactivate/complete/expire_attempts`、`routing.py` 的 `admit_source`、`deliveries.py` 的结果投递与核对。真实和合成验收范围分别见[3.0 发行说明](MASTERAGENT_3_RELEASE.md)及[3.1 进度](MASTERAGENT_3_1_PROGRESS.md)。

[接管文档](MASTERAGENT_3_TAKEOVER_20261013.md)直接说明 3.0 尚不能替代现有 MasterAgent 或全体业务角色；[UI 覆盖清单](MASTERAGENT_3_1_UI_COVERAGE.md)也未给出旧页面逐页完整承接的验收结论。当前声明与代码仍关闭业务文件工具、原生审批和原生 resume。发行状态不应替代产品承接状态。

因此，Astra 的价值应放在边界、异常语义和可追溯交付上；日常迁移收益仍需后续真实任务证明。现有材料不足以认定它的总体产品贡献超过此前长期运行与广泛功能积累，也不足以反过来否定重构价值。

## 用同一标准记录失误和纠偏

| 案例 | 问题或代价 | 谁参与纠偏 | 保留的成果与边界 |
| --- | --- | --- | --- |
| Opus 标签的 UI 拆分后 SSE 失效 | 接口可连接未覆盖变更事件真正到达 | Sonnet 标签补丁及历史复核 | 模块化有价值；端点健康不等于完整行为正确 |
| Opus 标签提交的 daemon 试点、扩张与回退 | 单角色可执行不能证明团队仍能交流、接受纠偏 | 用户指出方向损失；MasterAgent/Master数分联合复盘 | 保留可复用机制与治理经验；决策责任不由提交标签独占 |
| Fable 标签的悬单判据及修订 | 将正常退出误判为孤儿，可能重复处理 | Master数分反馈、后续 Fable 标签补丁 | 加固和回归场景扩大；不能宣称全场景正确 |
| 心跳与 UI watcher 的组合问题 | 已有监听策略与增加的写入共同放大刷新 | 用户反馈、Opus 标签 UI 补丁、跨角色验证 | 新等待机制和性能修复各有价值，不能简单归为单方错误 |
| Astra 主力阶段的 UI 覆盖遗漏 | 新入口分类未充分承接用户原有工作流 | 用户指出差异，补清单并吸收双方审阅 | 补目录是澄清范围，尚不是完整解决迁移 |
| Astra 3.0 首轮真实验收失败 | 原生生成目录触发预检，重复登录造成部署负担 | 开发修复、用户认证操作及限定授权 | 最终候选真实通过，失败历史保留；部署体验仍有待改进 |

这些是有记录的代表案例，不是完整缺陷样本，不能按案例数量给模型打错误率分数。旧系统经历的真实使用时间更长，新核范围更窄；场景、权限、工具环境和目标也不同。

## 模型贡献的修订判断

| 对象 | 当前最有依据的贡献定位 | 评价边界 |
| --- | --- | --- |
| Opus | 用户确认的初始主要协作者，参与长期产品建设、状态与引用契约、模块化、验证治理及后续修复 | 初始快照不是逐组件作者认证；集成提交需分辨实际实现者 |
| Fable | 参与代码审计、并发加固、前后端产品交付、等待身份机制及兼容运行条件下的平台化 | 既修正旧问题，也有新增误判；不能独占多角色验收或先前 UI 成果 |
| Sonnet | 提交记录明确关联控制台行为修复、写边界和运维功能 | 记录的是声明参与，不认证底层模型或独占作者；价值不由 12 条提交决定 |
| Astra | 用户与立项文档确认的十月重构主力，形成有真实纯文本验收的独立核和继续开发的工作台、持久通道 | 阶段归属不等于每个模块作者，3.0 发行不等于生产替换，3.1 尚未完整交付 |
| 用户及协作角色 | 产品方向、约束、试点选择、实现、口径复验、运行维护、错误发现和发行范围决策 | 既记录正确决策，也保留共同试验与返工；不把角色名换算成模型名 |

这比首轮更重视三项价值：用户实际依赖的旧产品能力、跨模型修复与继承、新架构已经验证但尚未完全转化为日常工作收益的部分。三者应分别表达，不合成为缺少依据的总分。

## 归因修正与十月独立维护

`2f3da99` 明确写着“改动 by Master数分(ctx口径owner)·MasterUI 重载+提交”。修订结论是：**Master数分修改、UI 集成、提交声明 Opus 协作；具体实现模型未知。** 首轮 C08 中把该项直接作为 Opus 上下文修复贡献的依据过强，今后不再沿用。Opus 的其他长期参与证据仍成立。

十月还存在旧 bus 与 WebUI 的 Codex 兼容维护。[旧 UI 巡检](CODEX_UI_AUDIT_20261012.md)记录 21 个页签的浏览器检查及适配修复，属于实际维护成果；它又明确没有进行相关写操作的端到端验收。末段显示的 `gpt-6-sol` 是当时界面报告标签，不证明维修作者，故不据此新增一个已认证的模型贡献份额，也不将这批工作并入 Astra 独占成果。

执行清单的 34 项也应按状态使用：B-00～B-06 已有相应完成或限定完成记录，B-07 未开始，B-08 部分进行中，其余依实际状态继续推进。清单与归档降低交接成本；其中已做和未做的工作不能重复计功。

## 未来开源介绍的修订候选

> MasterAgent 在创作者持续定义需求和组织验证的过程中演进。创作者确认最初主要使用 Claude Opus；项目记录随后显示 Opus、Fable 和 Sonnet 存在交叠协作，涉及总线、控制台、可靠性、运维及业务平台化。各阶段也通过用户反馈与跨角色复核纠正了局部和系统性问题。2026 年 10 月，项目进入以 Astra 为主力的重构阶段，在本机发行了经过真实纯文本验收的 3.0 独立协调基座，并继续推进 3.1 工作台与持久交接。旧运行体系的迁移和更广泛能力仍按独立验收逐步实施。

这段候选保留阶段主力，避免把提交署名当作逐行作者证明，也不暗示模型能力依次全面超过前代。具体公开模型名称和届时版本状态在正式写作时再核对；工具访问背景不进入该段。

## 本轮核查范围

本次核对历史提交正文与代表性源码差异、项目文档及现行能力声明；三路审阅分别检查旧系统贡献、新核交付与归因方法。它们属于同一任务中的交叉审阅，不是外部独立复现实验或多模型能力评测。

首轮 22 份来源文件摘要核对未变，原稿和原始账本保持原样。新账本保存本次来源、摘录、提交关联及修订结论。没有读取私人会话、生产邮箱或凭据，没有重跑历史测试、调用验收模型、启动服务或对外发布。当前部署是否在稍后发生变化不由历史快照推断；未来追加实际采用与长期运行证据时再更新相应判断。
