# Astra 输入：审阅 MasterAgent 3.1 开发版并决定下一批调整

日期：2026-10-19。此输入接续 [原平台审查任务](ASTRA_PLATFORM_REVIEW.md) 和 [3.0 审查报告](../ASTRA_PLATFORM_REVIEW.md)，不重新从零开展架构普查。先做只读审阅和实施顺序建议；不要在本轮修改实现、启动或停止服务、迁移状态、接管旧 fleet、读取无关会话或外发本机资料。工作树已有大量未提交修改，保留它们。Astra 不是运行时唯一模型；Claude Code 目前不可用，只保留有依据的适配契约，真实验收以 Codex 为准。

## 当前基线：先核对，再提出调整

- 3.0.0 是正式发行，schema 4。3.1 当前源码和独立开发包为 `3.1.0-dev.2.1`，公共 API 标记仍为 `3.1-dev1`。开发包 SHA256 `59e3d1c33e1f5ea1c2cebcc6c61cb8597690ed038bfabc045e45bfa4c8fb84c3`；MasterAgent 于 2026-10-19 重新核对本机包摘要，与 [实施进度](../MASTERAGENT_3_1_PROGRESS.md) 一致。这只证明审阅对象版本，并非重新运行功能验收。
- dev.1 只读五入口工作台、dev.2 第一批四项公共操作及兼容导航、dev.2 第二批服务端模型报告/累计 token 用量/原生请求拒绝记录已有各自合成验收。证据范围、数量、浏览器结果和限制以 [实施进度](../MASTERAGENT_3_1_PROGRESS.md) 为准。3.1 尚无新的真实 Codex 模型验收，也未接管旧 fleet；3.0 专用验收目录的认证授权不延伸到 3.1。
- 原生工具审批只有 [实施契约](../MASTERAGENT_3_1_NATIVE_APPROVAL_CONTRACT.md)，没有 schema 5、审批持久层、可批准按钮或已验证的 Windows 工具隔离。当前纯文本执行自动拒绝原生工具请求。工作台默认只读，`--enable-commands` 只开启已有公共命令。
- 旧 UI 21 个入口现有目录、范围说明及显式本机兼容链接；目录和链接不等于原生迁移或旧服务可达。逐项缺口见 [UI 覆盖清单](../MASTERAGENT_3_1_UI_COVERAGE.md)。当前包不能据此替代旧控制台。
- 3.0 [接管工作态](../MASTERAGENT_3_TAKEOVER_20261013.md) 指出旧 bus 与 V3 尚缺单入口路由、持久 ID 映射和结果回执。旧 fleet 与 3.1 合成工作台是两条不同运行线，不能把两边人数、任务或通知合并成一个在线事实。

## MasterAgent 的待审调整建议

以下是基于源码与文档的审阅建议，不是已经实现或已发生线上故障的结论。请逐项给出采纳、修改或驳回理由，并标明证据等级。

1. **先确定真实接管的最小闭环及实施顺序。** 当前 [3.1 方案](../MASTERAGENT_3_1_PLAN.md) 将原生审批列在 dev.2、持久路由和目的端投递列在 dev.3；但旧 fleet 接管至少需要单入口、领取归属、结果回执和不明状态核对。比较两种次序：先做仅纯文本的小范围真实单入口闭环，再开放工具审批；或先做隔离与审批再接管需要工具的角色。无论哪种，不允许旧 bus 与 V3 同领同一任务，也不以工作台任务提交成功推断模型接单。给出最小试点角色/任务条件、停接纳与回退边界、在飞工作核对和消费方通知。
2. **把审批部署前置闸做成可实施决策。** 契约要求工具权限为业务声明、角色部署、平台策略与实际 OS 隔离能力的交集；尤其 Windows 命令的间接访问、文件链接/重解析点、网络边界不能靠 cwd 或字符串白名单保证。请评估先支持 `command`、`file_change` 中哪一种，或者保持全部拒绝直到可验证隔离就绪；明确对应平台策略、schema 5 迁移、停止竞态与 `sending/held` 不重发的交付门槛。不要把平台 `Decision` 复用为原生批准。
3. **收敛 21 个旧 UI 入口的原生迁移范围。** [覆盖清单](../MASTERAGENT_3_1_UI_COVERAGE.md) 证明目前大部分仍为兼容访问或局部对应；原 [Astra 审查输入](ASTRA_PLATFORM_REVIEW.md) 曾要求按使用证据决定保留、合并、可选或退役。请按真实用户工作流和消费方把 21 项分为本次真实接管必需、兼容保留、独立扩展及待决定，不因为已有目录就全量移植。明确源标签、未知值、在线与租约、通知 delivered 与用户已读、旧 TODO 与 V3 Task 的不同语义。
4. **在 dev.3 前固定公开数据与版本边界。** 现行源码 `masteragent/workbench.py`、`workbench_query.py` 与 `workbench_commands.py` 仍返回 `api_version=3.1-dev1`，但 dev.2.1 已增加运行事实字段；schema 5 审批与后续兼容投递还会增加公共数据。请确定哪些为兼容附加字段，哪些需新的 API 版本及客户端协商；为旧 3.0/schema 4 读者、新写者、显式迁移与回退定义矩阵。不要让 GET 或启动工作台暗中迁移。
5. **真实验收要验证投递和角色能力。** 开发包的当前记录主要是合成数据、协议替身与桌面浏览器；服务端报告模型不证明实际推理模型，累计 token 不等于历史用量或账户额度。请为真实 Codex 单角色→双角色闭环设计隔离验收：精确身份、接单、执行期间补充、停止、结果送达、断线后的不明状态、恢复与旧 bus 不双领。认证范围须单独明确，不能借用 3.0 验收授权。状态展示要区分租约有效、信使可投递、模型实际可交互。

MasterAgent 的初步顺序建议：先固定持久单入口与回执契约，用隔离的纯文本任务验明跨线投递和恢复；需要工具的角色继续留在旧线，待部署隔离与独立审批过闸再迁。请 Astra 用依赖、交付时长和真实风险检验此顺序，必要时提出更优替代方案。

## MasterUI 独立审阅：用户路径的五项调整

MasterUI 于 2026-10-19 只读审阅了文档和工作台实现，完整证据与待验证项在 [UI 审阅结果](../ASTRA_3_1_MASTERUI_REVIEW_20261019.md)。以下不把静态审阅说成浏览器或生产验收。请将这些建议与上面的架构顺序一同取舍。

1. **P1，任务保存后的交接可见性。** 表单和回执已说明“保存到 V3 队列、等待独立执行服务”，但顶栏“公共操作已启用”只表示网页可写。建议在保存回执旁显示所选业务/代次是否存在可接单成员、任务是否已被领取、无人接单时的下一步；不能把成员租约当模型连通证明。依据 `masteragent/workbench_assets/views.mjs:86-90,299-320`、`commands.mjs:40-44`、`app.mjs:81`。
2. **P1，跨代次任务链的可达性。** 当前详情仅提示 `history_available`，所选代次的任务、Attempt、决定和结果可以看，其他代次的关联链不能直接打开。建议增加按代次与尝试关联的入口，明确当前过滤视图不是历史时点快照。依据 `masteragent/workbench_query.py:332-373`、`views.mjs:263-265`；需用续接和截断数据场景验收。
3. **P1，平台决定与原生审批在概览分名。** 当前概览的“待确认事项”实为平台 Decision；当独立 RuntimeApproval 落地时应有不同入口、数量、通知和答复状态。决定页已有“不等于原生工具审批”的解释；建议概览直接写“平台决定待答复”。依据 `views.mjs:104-123,223-237` 与审批契约；双待答并存尚未实测。
4. **P2，公开事件快照的时效和截断。** 顶栏已有 `observed_at`，页面失败时保留旧快照，但旧目录仍有“实时”入口。建议时间线附近显示最后快照时间、截断和断线说明；持久游标/断线补读验收前不宣称实时。依据 `app.mjs:42-79,164-174,257-264` 与 [工作台说明](../MASTERAGENT_3_1_WORKBENCH.md)。
5. **P2，按使用场景迁移旧控制台能力。** 21 项目录只证明说明和显式深链已构造。wait/selfwake、上下文、历史用量、提示词来源、任务线和工作组仍有明显能力差异。请根据值守、诊断、任务组织等真实场景排列迁移/兼容顺序，并验旧服务新版页面深链、旧版页面与离线状态；未等价承接前保留兼容回退。依据 [覆盖清单](../MASTERAGENT_3_1_UI_COVERAGE.md) 与 `masteragent/workbench_assets/navigation.mjs:5-43`。

本轮协作也观察到一次旧 bus 的长结果回执只保存引言；MasterUI 将完整结果写成本机文件后重新回报。原因尚未判定，不作为 3.1 缺陷结论。设计 dev.3 投递验收时，应包含长文本结果的完整性、来源 ID 对齐与不完整结果的显式核对。
