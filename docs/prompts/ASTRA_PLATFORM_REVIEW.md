# Astra：在线 Agent 团队协作平台审查与升级设计

请审查 `C:\apphome\agent_fleet`，为重构优化升级和以 Codex CLI 为主的在线 Agent 团队协作平台制定方案；为未来 Claude Code 接入保留必要接口。

本轮仅调查、设计和讨论：不修改实现，不启动、停止或重启服务，不注册角色、不派发任务、不清理运行数据。可以将审查报告写入项目 docs，保留工作区已有修改。

## 用户目标与判断标准

项目的核心是在线 Agent 团队协作平台：多个 Agent 具有明确身份、职责和状态，可以持续协作、分派任务、交换结果，并让用户看见团队在做什么、介入决策、恢复中断工作。

现有实现基于 Claude Code，但用户已明确：目前 Claude 完全不可用。本次所有可运行能力、实现与验收均以 Codex CLI 为主，Claude 只保留未来适配接口。Astra 是本次审查与改造使用的主力模型，不是平台唯一允许的模型。

这项前提优先于旧文档中的 Claude 运行、恢复、角色上岗和回归要求。不要把修复 Claude、启动 Claude、获得 Claude 凭据、验证 Claude 执行或组建混合团队设为本次工作的前置条件，也不要因此阻塞重构。现有 Claude 代码可作为行为参考；有价值的协调机制迁入公共核心，失效或耦合的实现允许重构、禁用或退役。历史数据与会话按价值保留，不因 Claude 不可用而直接清空。

项目包含用户已经不用的遗留功能，也包含尚未优化好的设计。不要把“现有功能全部保留”“现有架构全部正确”当作前提。以团队协作目标衡量价值，区分核心能力、可选扩展、业务专属内容、重复机制、过时设计及退役候选。没有使用证据时标记待确认；不要仅因没有静态调用或文档陈旧就认定可以删除。

## 调查要求

1. 阅读 README、AGENTS.md、相关架构与操作文档，并核对实际代码。区分现行行为、历史记录、设计意图和未完成计划。仓库中的历史角色说明不代表你应自动成为该角色或连接正在运行的团队。
2. 梳理角色加入、身份绑定、在线状态、任务派发/领取/执行/回填、Agent 间请求应答、用户介入、异常恢复、退出和退役的完整链路。
3. 评估“在线”状态的真实性：进程活着、会话可交互、正在监听、能够接单、忙碌和失联是否清晰区分。核对文档与实际机制，不凭状态标签假定 Agent 可以被唤醒。
4. 梳理前台可见 CLI 会话与后台非交互 worker 的职责和关系，调查是否存在重复领取、重复执行、身份串用、过期心跳或上下文丢失。
5. 找出 Claude 专属耦合点，覆盖命令启动、事件流、进程识别、会话恢复、hooks、权限、记忆、路径、用量统计和 UI，提供文件位置及行为依据。
6. 审查模块边界、重复实现、状态真相源、故障处理、配置、可观测性和测试。优化建议必须对应具体问题、收益和代价。
7. 调查功能的使用证据：入口、调用关系、配置、测试、文档和必要的本地运行记录。避免批量读取业务消息、完整会话历史或无关个人会话；不得读取凭据或向外上传项目资料。
8. 检查工作区已有修改，识别源码、配置、运行态、业务数据、宿主文件、junction/硬链接的边界，避免将重构变成在线数据迁移事故。

## 功能取舍

建立功能清单，逐项分类为：保留、优化、合并、可选扩展、退役候选、需要用户确认。

每项给出：服务的用户场景、代码依据、使用证据及其局限、依赖与消费方、维护成本、建议和理由。重点找出不再服务团队协作目标的历史包袱，不因为改动容易就优先处理。

退役候选需说明禁用、观察、迁移、删除和恢复路径。源码功能退役与历史数据清理分开处理；本轮不实施删除。

## 目标架构要求

- 平台核心与业务负载分离，支持空载运行和换业务域。
- 以团队协作为核心整理架构；不预设必须沿用全部现有机制，也不预设必须更换文件总线。提出最小演进方案与必要的替代方案，并比较代价。
- 区分 runtime、model、role、session、task。当前实现运行时是 Codex CLI，模型选择是另一层；Claude Code 为未来扩展，直接 API 执行是否需要列为独立决策。
- 公共协调契约与运行时专属行为分离。适配层覆盖启动、事件规范化、终态、取消、超时、权限、身份、恢复和统计；不要把不同 CLI 的参数或行为强行等同。
- 明确前台与后台执行的能力差异，表达无法支持的能力和退化行为，不能用虚假的在线状态掩盖差异。
- 新会话历史按 Codex 原生方式保存；历史 Claude 会话不假定可以直接由 Codex resume。需要继承的知识与任务上下文通过可移植工作状态接续，区分任务接续与原生会话恢复。
- 为 Claude 保留有依据的运行时接口、能力声明与扩展位置即可，不要求实现可用 Claude 适配器。未实现能力明确标为不可用；允许通过契约测试或测试替身验证扩展边界，但不能宣称完成真实 Claude 兼容验证。
- 核对任务幂等、领取所有权、结果关联、超时回收与重试语义；对可能重复产生副作用的任务给出处理方案。
- 用户能看清谁在线、谁接了任务、执行进度、结果、失败原因和需要介入的事项。
- 调查现有权限设计及其实际执行边界，不将一个运行时的跳过权限参数直接复制到另一个运行时。
- 根据当前官方资料验证 Codex 接入方案；无法验证的能力标记待验证，不编造命令、事件协议或兼容性。

## 后续阶段性任务简述

以下是整个项目的长期路线，不是要求首轮全部执行的固定施工清单。你可以根据审查证据调整阶段边界、合并工作或提出更好的顺序，但须解释原因。用户确认总体方向后，在获准阶段内自主决定具体设计、实现细节和必要验证，不必为每个常规技术选择询问用户；目标变化、重大取舍和影响在线团队的切换需要明确提出。

### 第一阶段：认清现状，确定平台方向

弄清团队如何真正协作、现有机制是否可靠、哪些功能仍有价值。产出架构审查、功能取舍和推荐路线，形成可以讨论的结论。不要把本阶段变成无限考古；优先调查会影响后续设计的关键问题，证据不足项单独列出。

### 第二阶段：收敛遗留功能，优化核心设计

围绕在线团队协作收敛平台边界，处理确认不用的功能、重复机制和不合理设计，减少配置与状态混杂。优先解决用户体验和协作可靠性的实际问题。现有有价值的能力应在 Codex 路线上延续；需改变的行为说明原因与迁移方式。完成标准是平台职责更清楚、关键链路更简单，已确认的遗留包袱得到处理，公共协调机制建立不依赖 Claude 的验证基线。

### 第三阶段：重构公共协作核心与运行时边界

将角色、在线状态、任务流转、团队通信、用户介入、恢复和观测整理成清晰的公共契约，解除公共核心中的 Claude 专属耦合，以 Codex 接入需要确定运行时边界。按实际复杂度选择抽象，避免提前建设过大的框架。完成标准是核心协调逻辑不依赖 Claude 专有细节，公共核心通过有意义的验证，Codex 有明确接入位置，Claude 有最小必要扩展接口。

### 第四阶段：全面接入 Codex，打通团队执行能力

让 Codex CLI 成为默认且完整可用的团队执行运行时，支持按角色或任务选择可用模型。先打通完整任务闭环，再完善身份识别、在线监听、事件展示、取消超时、会话恢复、记忆注入、统计及前台/后台模式。具体接入方式由你结合官方能力和平台需要选择。完成标准是 Codex 团队成员能够真实执行并回填任务，不依赖 Claude 命令、hooks 或宿主配置才能工作；无法支持的能力明确可见，错误可诊断，没有假在线状态或静默降级。

### 第五阶段：验证 Codex 团队协作与日常体验

验证多个 Codex 成员之间的派发、请求应答、结果交接和工作状态接续，以及离线、崩溃、超时、重复领取和恢复等关键场景。优化用户看到的团队状态、进度、结果和待决事项。完成标准是 Codex 团队能协作完成有代表性的真实工作，平台状态与实际执行一致，出现故障时用户知道发生了什么、如何恢复。Claude 混合运行属于将来单独实施的扩展，不计入本次验收。

### 第六阶段：稳定运行，完成迁移与交接

完善以 Codex CLI 为主的启动、配置、诊断、升级、回退和操作文档，在隔离验证后安排切换。核对旧功能退役与历史数据保留，确保新的使用入口清楚。完成标准是新会话可以凭项目文档恢复工作，平台在没有可用 Claude 环境时也可以重复部署和验证，用户能独立使用和维护这套团队。

### 每阶段的工作方式

- 先说明本阶段要解决的具体问题和预计结果，再实施；小范围常规选择自行判断。
- 按可审查、可验证、可回退的增量推进，不以改动文件数量衡量进度。
- 每阶段结束简述：完成了什么、行为如何变化、验证证据、剩余问题和下一阶段建议。
- 在适当位置持续维护精简的进度记录，保留关键决定、理由和下一步，便于换会话接续。
- 允许你主动提出超出初始清单的改进，但应与在线团队协作目标直接相关，说明价值和成本；重大范围变化先讨论。
