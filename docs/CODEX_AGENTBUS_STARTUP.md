# Codex agent-bus startup

This is the Codex-specific fleet bridge. Both role-memory injection and bridge startup are registered user-wide through `~/.codex/hooks.json`. Project `.codex/config.toml` files retain a fallback bridge entry and the MasterAgent compact card; a per-session OS lock prevents the global and project startup hooks from creating duplicate bridges. A recipient does not manually run `ab wait` in the Codex session.

## Prompt layers

The host-global Codex rules have one physical source, `host_config/CODEX.global.md`, exposed through `~/.codex/AGENTS.md` (currently an NTFS hard link). In this repository, `AGENTS.override.md` is the short Codex project entry; the large `AGENTS.md` and `CLAUDE.md` remain historical Claude/legacy-bus references to read only for relevant work. Startup/resume hooks provide the exact role card, capabilities, and project memory entry point. A long memory index is exposed by path for task-scoped reading. Compact recovery re-injects the concise MasterAgent card and role memory entry point. The shared Claude role profile still records its old manual wait procedure and lists `agent_fleet/AGENTS.md` as a boot read; the Codex context hook replaces the procedure with the messenger rule and omits that legacy boot read, preserving the event-driven delivery requirement. Business project `XXX` keeps its own `AGENTS.md` and the short `CLAUDE.md` hook injection because they contain customer-repository boundaries. The WebUI prompt-audit page shows these layers and live hook previews separately.

## Identity rules

- Codex `whoami` accepts only an exact, non-empty session-id match in `presence.json`. It never falls back to `codex_pid`, because one Codex host process can serve multiple threads.
- A registered Codex session also has a local durable entry in `agent_bus/codex_session_roles.json`. On `SessionStart(startup|resume)`, the hook may restore a cleared or stale presence only when the ledger and that role's last `presence.host_session_id` agree on the exact session ID. If the host kind was cleared, the prior messenger state must independently name that same session. The hook runs inside the resumed Codex process, refreshes presence, then loads the role card and starts the messenger. It never selects a role by shared PID or cwd. A new session still needs an explicit role ticket.
- The `SessionStart` event carries the exact `session_id`; the 2026-10-14 resume showed that these hooks cannot rely on inheriting a matching `CODEX_SESSION_ID` environment variable. Hook entry points now reject a conflicting inherited ID, then set that variable from the event before exact-host restoration. A registered resume that cannot rebind the current Codex host fails before launching a messenger. The detached messenger's internal wait validates that same live exact binding before registering, records its host PID from presence only after the session match, and may then refresh `last_seen` and mode without erasing `host_kind` or `host_pid`.
- A new thread has no role in Codex's `SessionStart` event. Arm one explicit, project-scoped assignment before opening it:

  ```powershell
  python -B C:\apphome\agent_fleet\agent_bus\agentbus.py codex-role-next --role 示例成员 --cwd C:\BaseSpace\XXX
  ```

  The context and startup hooks share one atomic claim. The first matching, non-empty session reserves the ticket before any role profile or memory is read; repeated calls from that same session and cwd are idempotent. The startup hook then runs `hello` and starts the bridge. Eligibility, cwd and expiry are checked on each ticket access. The assignment expires after 30 minutes and cannot be overwritten while pending or reserved but not yet registered. Another session cannot read that role context through the reserved ticket. If no assignment matches, startup leaves the thread unbound.
- If a user explicitly assigns a role only after the new Codex thread has already started, an `ab hello --role <role>` from that exact thread now registers the role and starts its detached messenger. Its output gives the Codex-specific self-wake instructions and role/memory pointers; it does not tell Codex to run the Claude manual wait. The initial developer-level `SessionStart` context cannot be retroactively injected into an already-running turn; the next resume or compact loads it. A repeated hello cannot change a session already durably registered to another role.
- Do not set a project-wide default role for a workspace shared by Master and business agents. A default would silently register every thread in that workspace as the same role.

## Lifecycle

`SessionStart(startup|resume)` runs the user-global role-context and messenger launcher hooks. The global context hook skips startup/resume where a project context hook already supplies the same role context. A synchronous context hook first restores an existing exact-session registration from the durable Codex ledger when needed, then injects the selected role profile and resolves the memory index from that role's `memory_cwd` when declared, otherwise its project `cwd`. This lets a role execute from the bus workspace while retaining its own project memory. New threads still require an explicit one-shot role ticket. It prefers `<role>.MEMORY.md`, then falls back to that project's `MEMORY.md` router, matching the Claude memory layout. When a curated role index is absent, it also discovers matching `memory/roles/<role>-*.md` extracts from the resolved role's project: one concise note is injected, while multiple notes are exposed as task-scoped read targets. Identity is resolved before this lookup, so filenames never assign a role. The short launcher uses Windows CIM to create a detached `pythonw.exe` messenger, waits for its first armed heartbeat, then exits. The hook's timeout limits only this launcher, not the messenger's lifetime. The messenger verifies its session id against the selected role's presence, atomically claims the current inbox backlog under its long-lived process, and confirms a new registered wait before starting the first turn. Its internal wait pump stays armed during model work, claims and queues later messages, then sends them in order after the active batch finishes. Approval-gated tasks remain in inbox.

The user-global hook source is `agent_fleet/host_config/CODEX.hooks.json`, hard-linked at `~/.codex/hooks.json`. Project fallback hooks live in `agent_fleet/.codex/config.toml` and `XXX/.codex/config.toml`. The role bridge implementation lives in `agent_fleet/.codex/`.

Codex async hooks do not provide Claude-style wake-on-background-task-completion: completed background-hook output is delivered at a later safe point, and with no active turn it waits for the next user turn. The bridge therefore uses the local App Server control protocol to start a turn on the exact bound thread. It now reconnects that same thread after an App Server daemon restart while the bridge process remains alive. A disconnect during an active model turn is treated as an uncertain outcome and is not automatically replayed; this avoids duplicating side effects. `wait.reg.json` alone means the bus wait is registered, not that the App Server delivery channel is connected.

The messenger writes `agent_bus/<role>/messenger.state.json` every 10 seconds with exact session id, PID, wait process, pump and App Server readiness. `selfwake` marks a matching heartbeat older than 35 seconds stale and a live but incomplete delivery chain degraded. A bus wait alone does not establish Codex delivery. The local WebUI runs `.codex/codex_messenger_guard.py` every 45 seconds; `ab selfwake-guard` also invokes the same recovery path. It re-arms only a recently active, exact-session Codex role whose messenger process is gone and whose processing queue is empty. The shared host PID is used only as a liveness gate, never as identity. The guard skips parked roles and maintenance mode; active turns, a live but degraded messenger, stale sessions, missing exact bindings and unfinished processing are not automatically restarted. A failed launch is eligible for reporting after a 30-second batching window; an unresolved blocked recovery after 90 seconds. All ready incidents in one scan produce one MasterAgent task, with per-role details retained in `messenger.guard.report.json`. Codex roles never receive the legacy manual `ab wait` reminder. The guard never replays a claimed task. Attempts are recorded in `agent_bus/codex_messenger_guard.jsonl` with a three-minute per-role cooldown. An in-flight or fenced task still requires reconciliation. `codex queue` is available in the local CLI and its help describes queueing to an existing session. A probe with a synthetic nonexistent name returned `No active session found`; that does not establish how it handles a saved thread detached from the current App Server.

On 2026-10-15, 示例成员2 completed a task and wrote matching `ok` records to its archive and Master's done inbox, but the old processing file remained. The messenger treated that duplicate as `missing_task_receipt` and stopped; the guard correctly refused to replay it. Infrastructure checked the exact claim ID, sender receipt, result and idle turn, preserved the duplicate under `_codex_recovery/completed_processing/`, and restarted the messenger on the same registered session. `reconcile_unfinished` now recognizes this precise archive/receipt pair and preserves a residual processing file without re-executing the task. `reap` will not overwrite an existing completed archive with an older processing payload. This code change has not had a separate fault-injection run.

### 24-hour hook expiry observed on 2026-10-12

The user-global and project fallback `SessionStart` bridge hooks both set `async` and `timeout=86400` seconds. Six previously listening roles (MasterAgent, Master, Master数分, 示例成员4, 示例成员3, 示例成员) stopped heartbeating on 2026-10-11 within seconds of the corresponding 2026-10-10 startup time plus 24 hours. Their Codex host processes were still alive, but their bridge and wait processes were gone. Two bridges started outside that hook lifecycle remained alive. This timing and Codex's documented background-hook timeout semantics identify hook expiry as the likely common cause; no per-hook cancellation trace was available to prove each individual exit. Maintenance mode had suspended the self-wake guard, so it did not attempt recovery.

The six exact-session bridges were restarted without rebinding roles or replaying tasks; `selfwake` then reported eight listening roles with eight bridge and eight wait processes. The subsequent detached messenger design removes the 24-hour hook lifetime limit and adds periodic health evidence. Existing bridge processes retain old code until restarted. Session-end cleanup remains separate work; the later WebUI guard repairs only recent, idle losses and leaves in-flight work for explicit reconciliation. Do not restore roles whose host session has exited merely because their old presence remains.

### App Server package switch and exact-session fleet recovery on 2026-10-16

At about 06:37 local time the App Server package changed from `0.162.1` to `0.163.0`. The old shared daemon PID 25692 disappeared and the new daemon PID 44592 started at 06:37:47. All 20 old messenger processes stopped within roughly ten seconds with `wait returned non-JSON output: `: their internal wait self-exited when its registered host PID disappeared, leaving the bridge no JSON result to parse. This common timing and package change strongly link the outage to the host switch; they do not prove why the Codex client updated or whether each CLI briefly lost its interactive connection. The guard refused to reuse the dead shared PID. At 08:49 only the resumed MasterAgent thread was armed; the other 19 had exact saved session IDs and live matching CLI processes, but stale presence bindings. No role had an unfinished business claim or inbox backlog.

Recovery used `codex queue --thread <exact-session-id> -C <role-cwd> --message <rebind-only instruction>` on one role first. GPCC's own session rebound its presence to PID 44592 and its SessionStart messenger became armed. The other 18 existing sessions were queued sequentially with a twelve-second gap, after checking each durable role/session match, matching live CLI process, and empty processing queue. No new client was started and no business task was replayed. Each group was checked for a fresh messenger heartbeat, registered wait and ready App Server pump. The final `ab selfwake` showed 20/20 Codex roles listening and zero offline. `codex queue` is therefore a proven same-session recovery path for this incident when those exact preconditions hold; it is not a general authorization to wake an unrelated or uncertain session. Automatic host-switch recovery remains a separate design change: the current wait exits on dead host PID, and the messenger stops instead of reconnecting after the wait's empty output.

## Current limitation

Codex does not include a role in `SessionStart`. A shared App Server process may host both Master and 示例成员 threads, and its process id does not distinguish them. Therefore an unbound thread cannot safely auto-select a role; the one-shot assignment is the explicit selection step. After registration, startup and resume recover the role by exact session id without another assignment. A stopped thread is not woken merely because its ledger entry exists; it must actually emit `SessionStart` on resume. The ledger does not replace `whoami`'s active presence check or prove that a messenger is armed.

### Same-session resume recovery after the 2026-10-12 App Server restart

At 12:03, the shared host changed and eight Codex messengers stopped within seconds. Detached wait heartbeats cleared `presence.host_kind` and `host_pid` when the old host PID died, while retaining `host_session_id`. The previous resume hooks required `host_kind=codex`, so restarting clients into the same saved sessions could not restore their role context or messenger. The durable `codex_session_roles.json` now records an exact session-to-role binding when a Codex session registers. On a later `startup|resume`, the hook requires the ledger, the role's current exact presence session ID, and (when host kind is missing) a matching prior messenger session ID before it refreshes presence from the resumed Codex process. This keeps a new thread unbound and prevents a stale older session from reclaiming a role already rebound to another thread. A one-time local ledger seed from the eight matching historical presence/messenger records is needed for sessions registered before this change; the seed itself does not start a messenger or claim work.

The eight historical records were seeded only after checking unique session IDs and exact agreement between each role's presence and messenger state. Existing resumed sessions then completed their own registration; MasterAgent restarted stopped messengers only for roles with a valid current Codex presence, a live host, no processing files and an idle turn. An App Server `thread/resume` RPC alone did not fire `SessionStart` for the remaining unbound 示例成员4 thread; that thread first registered from its own session, then its messenger was started. At 14:33 all eight roles had fresh heartbeats, exact presence/session matches, live registered waits, and ready App Server delivery pumps. This verified fleet liveness at that time, but not the next client restart.

On 2026-10-14 the next same-ID resume exposed the missing check: the startup hooks launched two messenger candidates at 09:23:03 while the registered role had not been rebound to the new Codex host. Their detached wait wrote presence at 09:23:07 with `host_kind` and `host_pid` cleared; the messenger stopped at 09:23:17 with `messenger exact session binding lost`. The current `whoami` then returned an unbound role even though its session ID still matched the durable ledger. The event-ID preparation, fail-closed launcher and bridge-wait presence protection above address this chain; a future real resume is still needed to confirm automatic restoration.

Windows AppX deployment events at 12:03:40–12:04:00 show Codex updating from `26.1002.7124.0` to `26.1007.2314.0`; the deployment terminated the old package service, and the new desktop App Server process started at 12:04:15. This strongly links the simultaneous fleet disconnect to the application update. The local logs do not establish why the old CLI eventually displayed `Automatic reconnect could not restore this session`, so do not claim that a bus change can prevent that client error. The durable exact-session ledger addresses the separate failure where a resumed client could not restore its role and messenger. It does not keep a CLI terminal or unsent draft alive across an application update. When a terminal requires relaunch, preserve any unsent draft and use `codex resume` with the same saved session ID; then check `ab whoami --json` and `ab selfwake` before considering delivery restored. Do not start a duplicate client automatically while an existing terminal may have an unsent draft or an uncertain active turn.

`ab resume` now lists Codex's exact `host_session_id` and a `codex resume <id> -C <project-cwd>` command when the durable session-role ledger and current presence agree. It uses the role profile's project cwd rather than the shared App Server daemon workdir. An online command is reference only; a stopped messenger with an unchanged Codex host is marked pending verification because the original client may still be open. A cleared host kind needs matching prior messenger evidence before the command is offered. The command never registers a new role or proves the resumed messenger is armed.

## Compatibility safeguards added on 2026-10-12

These changes repair the existing bus adapter. They do not connect App Server to the V3 Task/Attempt/Lease store, migrate business data, or change `masteragent` version `3.0.0-dev.3`.

- Claim and dispatch require the exact `presence.host_session_id`; cwd, shared PID and the legacy `codex_session_id` alias cannot grant this binding. The bridge checks the actual bus root before each claim, wait launch and model delivery. The wait subprocess also checks its explicit session at claim time. Rebinding a role cannot downgrade an existing Codex caller to an unprotected legacy claim.
- Before moving a Codex inbox task, the mailbox persists `<role>/_codex_recovery/<task-id>.json` with a unique claim and session binding. Before RPC delivery, the bridge checks that marker against the processing record and atomically reserves `claimed -> dispatching`. Missing, corrupt, mismatched or already dispatched markers refuse delivery. A marker write failure is fatal to that claim.
- Only the exact thread and turn ID returned by this batch's `turn/start` RPC can complete the batch. Early notifications are correlated after the response; unrelated turns do not release it. Failed, interrupted, unknown, disconnected or timed-out turns stop subsequent delivery and mark unfinished work `needs_reconcile`.
- A completed model turn is not a task receipt. Remaining processing records or missing completion evidence stop the bridge for reconciliation. A matching terminal archive or exact routed receipt supplies completion evidence; a processing file merely disappearing does not. Existing results and archives are not overwritten by recovery diagnostics.
- Both legacy `reap` and orphan recovery retain fenced tasks, including after role rebinding. Pre-upgrade processing under a currently Codex-bound role is also retained. This is a compatibility barrier, not a complete historical migration or an exactly-once guarantee for external effects.
- A registered wait whose host is confirmed dead is `stale`; a process-scan fallback cannot relabel that orphan `armed`. A healthy bus wait still does not by itself prove App Server delivery is connected.

There is no automatic fence deletion or retry command. When a task is marked for reconciliation, preserve its marker, processing/archive record and existing receipt. The operating session must first check whether an external effect or valid result already exists. Use the existing `done` flow only for a verified outcome; do not copy the original task back to inbox or remove its marker to force replay. If a retry is explicitly approved after reconciliation, retain the old evidence and submit a distinct request. Merely restarting the bridge does not resolve an uncertain result.

## Usage scope and verification boundary

Codex usage defaults to exact sessions bound to current roster entries. Missing roster/binding or no explicit scope yields no history access; unregistered old sessions are excluded from the default total. Cache scopes are rechecked when bindings change. Counts and latest-context selection are corrected, and `role_live: null` means unknown liveness. Claude statistics failure leaves Codex statistics independently available; either provider's failure is shown as unavailable, not successful zero usage.

Earlier compatibility validation used synthetic tickets, queues, rollouts and App Server events in temporary directories, plus frontend syntax and synthetic DOM checks. The 2026-10-12 messenger lifecycle change was additionally deployed to eight exact, already registered Codex sessions after checking their inbox and processing queues were empty. The startup hook returned while each detached messenger remained alive; state files showed fresh 10-second heartbeats, registered waits and connected App Server channels, and `selfwake` reported all eight as listening. No private session content was read.

The live communication probe then sent a harmless coded request from MasterAgent to Master (`1791773187965-Master-225564`). Master's messenger logged delivery into a Codex turn, and the result returned through the bus as `ACK-f8d171d2-43`, matching the requested nonce and arithmetic answer. A preceding probe's completion notice was delivered into the current MasterAgent Codex turn and acknowledged; the second notice was also archived with no inbox or processing remainder. The MasterAgent messenger was reattached to the same exact session after the probe and again showed a fresh heartbeat, registered wait and App Server readiness. This verifies a real message/result/notice round trip for these two sessions; it does not prove every role or failure mode.

On 2026-10-12 at 11:12, the MasterAgent messenger stopped with `invalid_delivery_fence` after a notice had already been completed and archived at 11:10. No new claim appeared in the bus event log. The bridge now drops a queued duplicate only when its task ID and claim ID exactly match a completed archive record and no processing record remains; all other items retain the delivery fence. The exact-session messenger was restarted and again reported a live wait and App Server channel. This fix has static syntax validation and live re-arm evidence, but the duplicate timing has not been reproduced in an isolated fault test.
