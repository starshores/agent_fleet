# Astra 3.1 开发审阅与交付顺序建议

日期：2026-10-19。审阅对象：`3.1.0-dev.2.1`。输入为 [双方意见汇总](prompts/ASTRA_3_1_DEV_REVIEW_20261019.md) 和 [MasterUI 审阅](ASTRA_3_1_MASTERUI_REVIEW_20261019.md)。本报告提出下一批调整，不改写原计划、实现、状态库或运行服务。

建议把下一阶段主线调整为：**先补齐任务交接和历史可达性，再交付持久单入口与目的端回执，用独立纯文本角色完成真实验证；工具隔离和原生审批并行准备，条件通过后另行开放。** 这调整了上一轮“先工具策略和审批、后存储投递”的顺序，沿用已经交付的协调内核、工作台和运行观测。

## 对双方意见的逐项取舍

MasterAgent 的五项建议均采纳目标，作三处修正：第一，先验证纯文本单入口闭环，不把工具审批作为所有接管的前提；第二，API 附加字段与数据库结构升级分开判断，审批文档里的 schema 5 改为后续实施时的实际版本；第三，第一轮双角色验证是平台编排的文本任务链，不是模型自主派活。

现有 `request_child` 只接受 queued/waiting 父任务，原生纯文本运行不能自主调用协调工具。因此可先由平台控制方预先建立父子关系，验证子结果进入父任务输入；不能把这种成功算作原生 agent 协作桥完成。【事实 S6】

MasterUI 的五项处理如下：

1. **采纳交接可见性。** 保存回执旁提供“查看已保存任务”，显示同业务/代次/角色的成员快照及时间，再展示领取归属。可接单只是租约与成员状态口径，不写成模型在线；没有成员给出执行服务未就绪的说明，不禁止保存排队。
2. **强化跨代次可达性。** 以 installation + task 建立稳定只读链入口，包含 continuations、各代次的 Attempt/决定/结果和分页；单独标注任务当前归属。保留当前代列表筛选和写操作守卫，不把读历史变成允许旧代操作。验收包括纯排队续接、旧决定、旧尝试、两次以上续接、截断和跨安装隔离。
3. **采纳平台决定分名。** 概览与通知先改明确称谓；未来原生审批拥有独立对象、入口、计数和答复状态。当前不制造一个可操作的原生审批入口。
4. **采纳详情独立快照时间。** 顶栏目前取任务列表快照，详情另行请求；详情应常驻自身 observed_at，显示“公开事件快照”。已有截断/断线说明继续保留。持久游标和补读交付前不宣称即时订阅。
5. **采纳保留兼容，修改全量迁移预期。** 按下表迁移用户能力，未承接部分保持明确去向；新版深链、旧版页面和离线分别验收。当前没有使用率证据，不据菜单数量决定全部原生重建或退役。

## 建议交付顺序

此处是替代实施顺序建议，尚未变更原计划批次和当前版本。工作量仅作相对比较，不承诺未经拆解的日历工期。

| 顺序 | 具体交付 | 依赖与放行条件 | 相对工作量 |
| --- | --- | --- | --- |
| A 任务可见性与契约 | 跨代任务链、保存后交接提示、平台决定分名、详情时效；冻结路由/回执及 API 兼容契约 | 可继续用 schema 4；历史只读不放宽写守卫；当前查询及隔离回归通过 | UI 小改较小，历史链中等 |
| B 持久文本通道 | 核心库中的来源映射、路由代次、目的端投递账本；目的端去重接收；冻结新接纳与异常核对；显式迁移及恢复预演 | 先合成旧/新消费者竞争、崩溃与重复回执验证，再启独立真实单角色→双角色文本验收 | 较大，是主线 |
| C 存储与可观测性扩展 | 持久事件游标/断线补读、制品封存与索引、输入来源和备份范围、历史查询 | B 已有的路由与回执模型作为基础；大文本超出任一目的端上限时先明确拒绝/核对，不能等索引做好前静默截断 | 中等到较大，按独立能力拆批 |
| D 工具角色接入 | 可验证隔离、不可变工具策略、独立 RuntimeApproval、精确内容和答复发送、真实工具验收 | 仅在审批闸全部通过后开放；需要工具的角色此前留旧线 | 较大，隔离结果不确定 |

A 的界面工作、B 的领域设计、D 的隔离方案核查可并行；真实路由试点必须在 B 的排他与回执故障验证后进行。D 不必等待 C 全部结束，但不能跳过自己的准入闸。Claude 继续契约工作，真实 Claude 和混合团队验收单列，不阻塞 Codex 纯文本试点。

## 最小真实试点与回退

首个角色只处理显式提供的虚构文本，执行摘要、核对或格式转换；不读取业务文件、不运行命令、不依赖私人历史或自主派活。使用独立业务包、状态根、角色部署、原生 home 和固定可执行版本。认证范围为本次试点单独确认，不借用 3.0 目录间复用授权。试点不直接迁入 Master、MasterAgent 或其他需要工具的现任角色。

先在独立旧线测试入口与新平台之间验证真实传输，再由运行负责人选择小范围消费方灰度。业务角色名、消息翻译和流程位于业务包/兼容适配层，不进入基座分支；同构建仍须通过 A→B→A。

最小放行证据：

1. 来源 namespace/ID、内容摘要、路由代次和目标绑定持久保存。相同 ID 相同内容返回原任务，同 ID 异内容拒绝。所有旧领取路径与新执行器共用可验证的排他规则，不能只改 `ab send`；request、通知、工作组、待办、WebUI 等来源要么纳入，要么明确拒绝/留旧线。
2. 单角色真实完成保存、领取、执行期间补充、结果产生、目的端接收；分别记录补充已保存/已发送/已接收、租约/可投递/模型交互证据。再验证停止、断线与不明状态恢复，迟到旧执行不能发布。
3. 双角色使用平台预编排父子任务，验证角色作用域、子结果归属、父任务恢复及重复回执；不宣称模型自主协作或跨运行时原生 resume。
4. 原生最终文本、平台结果和目的端保存内容逐层比对 UTF-8 字节数与 SHA256，保留可逆 ID 链。中文、emoji、长行、多段 commentary 后 final、尾段哨兵、边界大小和回执乱序均纳入。输入中“长回执只剩引言”的观察原因未定，不归咎于 3.1。
5. 在来源领取已持久化但核心事务尚未提交、核心事务已提交但旧来源确认未回填、目的端已写但回执丢失、结果写入后发送前等崩溃点恢复。核心来源映射与新任务必须同事务提交；跨存储域的确认仍需核对。可按同一 ID 查询/重试幂等接收；目的端无法查询时转待核对，不新造消息或重新执行模型。

回退先冻结新接纳并记录边界，已有消息保持原归属。若选择自然排空，应先禁止新 claim，再等待在飞任务结束；现有 member stop 会 fence 活跃 Attempt，不能冒充已实现的 drain。【事实 S7】

运行负责人需逐项核对来源消息、task/attempt/member、未确认补充、结果、目的端回执及拥有者退出证据。租约到期不证明进程已退出；不明项保留 needs_reconcile/held。回退只改变未接纳的新消息去向，不搬回旧 inbox、不覆盖新库、不重放旧成果。切换前形成消费方说明：范围、入口、状态解释、冻结/回退操作和未决清单；本轮没有代发通知。

## 关键契约差距与验收

| 领域 | 当前缺口与建议 | 验收及失败处理 |
| --- | --- | --- |
| 路由与回执 | S1 已有核心幂等与事务结果，但缺跨线领取排他、来源映射、目的端 receipt 与发送领取。建议账本与 Task 放同一权威库；目的端用自己的持久接收 ID | 同一来源只生成一个原始任务，任一时刻只授权一方领取；不明执行不自动重跑，显式重试产生新 Attempt。同 ID 异内容拒绝；投递可重试且目的端去重，不能查询不明回执则 held。无跨文件/数据库原子性承诺 |
| 工具隔离与原生审批 | S4 无隔离实证。沿用三种交互分离、typed RPC id、单次答案、sending/held 不自动重发；实际 writer 的 flush 证据需关联 approval_id | 专用环境内验证允许操作及越界读写、网络、子进程、UNC/链接/重解析点、路径替换被阻止；验证停止与发送竞争。失败继续全拒绝 |
| schema 与 API | S5 精确结构校验，HTTP/UI 版本精确匹配。附加观察字段可兼容；新持久表必须显式升级，路由先落库则先占 schema 5 | 新旧客户端契约矩阵、迁移备份、忙碌拒绝、断电回滚、旧程序拒新库；无自动降级、GET 迁移或工作台启动迁移 |
| 身份 会话与记忆 | 平台 Actor/member/native thread 不能直接等同旧 bus 或桌面会话；试点需显式登记与部署映射。S8 原生 resume=false | 精确角色绑定、授权指令与输入来源清单；错角色/代次拒绝，缺记忆显式报缺，不扫描私人历史；跨运行时接续只交接工作态和成果 |
| UI 来源与状态 | S2 历史不可达；S3 可写不等于可执行、顶栏时效不等于详情时效；兼容目录无在线证据 | 以业务/代次/角色隔离的真实交接场景验收；无成员、租约过期、结果未送达、历史截断均可辨认；来源旧 bus/V3 分列，不能合并在线人数或队列 |

原生审批当前决策是 command/file_change 都不开放。隔离验证通过后，优先评估完整、限大小、单次的 file_change，再评估 command；这是范围更易限定的工程推断，不是文件变更已经安全。非空 grantRoot、无法完整展示的差异、额外权限、未知 environment、writeStdin、网络/规则修订继续拒绝。完整文件 item、移动目标与内容指纹须先于批准固定，不能只判断 cwd 或 grantRoot。

审批发送要区分入队、实际 write/flush、原生请求关闭、工具 item 终态；停止与在途字节之间存在不可原子化边界，未知效果保留核对。不得持有数据库事务等待用户或原生执行。原 [审批契约](MASTERAGENT_3_1_NATIVE_APPROVAL_CONTRACT.md) 的这些要求沿用，schema 编号按实际开发顺序调整。

## API 与数据库兼容建议

**现有 `api_version=3.1-dev1` 不是本轮缺陷证据。** 当前增加的是可选观测字段，既有字段含义、未知值及操作语义保持不变；旧客户端不认识新增字段可以忽略。应补冻结的旧响应样本/客户端测试，不仅测试当前包自己能读自己。

下一批在配置响应增加兼容的能力声明和契约修订号，客户端按能力显示新入口；这些字段不取代命令的领域守卫。新增独立任务链/投递/原生审批端点可在 v1 内附加，使用独立数据结构和验证器；既有详情仍保留所选代次语义。若要改变已有 source 语义、必填字段、枚举/状态含义或请求格式，则提供新的 API 版本及协商，不改旧接口的含义。现 UI 对版本字符串精确匹配，单方面改字符串会直接拒绝响应。【事实 S5】

数据库版本、API 版本和发行包版本各自管理。不要为复用 `api_version` 将 RuntimeApproval 塞进 Decision，也不要为了 schema 5 这个编号把尚未就绪的审批与路由捆绑发版。

| 组合 | 当前事实或目标规则 |
| --- | --- |
| 3.0 / 当前 3.1 与 schema 4 | 当前结构兼容，各程序仅提供自身版本的能力；这不授权两个执行版本并发处理同一任务或让旧读者理解新增运行语义 |
| 3.0 / 当前 3.1 与未来 schema N | 当前程序应因版本或表结构不符明确拒绝读写；不能只换旧二进制就回退 |
| 未来新读者与 schema 4 | 建议显式保留 schema 4 只读分支，关闭仅新结构支持的能力；此分支尚未实现，不能提前声称可用 |
| 未来新写者与 schema 4 | 要求显式迁移；新账本写入前校验完整新结构，不在 GET、首次提交或服务启动时创建表 |
| 新写者与 schema N | 使用已发布的唯一迁移清单；拒绝运行中任务/Attempt及仍有效 ready/waiting/busy/stopping 成员下迁移，先停接纳和核对 |
| 迁移或升级回退 | 事务失败回滚，保留一致备份。已有新版本写入后，先冻结和导出核对，不覆盖原库；在独立目录以匹配旧版本打开迁移前备份，新接纳和未决项继续保留在原账本 |

建议路由表进入核心 SQLite，避免再增加一个权威任务库。旧 bus/目的端仍是另一存储域，接收提交和平台回执通过幂等与核对衔接，不声称跨域 exactly-once 效果。WAL、数据库服务或 Redis 不作为本轮前置变化。

“试点必需”仅要求其中的最小用户能力，不要求搬入整页；所有未等价承接部分继续保留兼容访问。“独立扩展”和“待使用证据决定”都不表示退役。分类依据是纯文本试点流程，不是实际使用率。

| 旧入口 | 分类 | 本次边界 |
| --- | --- | --- |
| fleet 舰队运维 | 试点必需 | 执行者、领取归属、租约/可投递/模型证据分层；自愈和旧宿主恢复保留兼容 |
| guide 操作说明 | 试点必需 | 保存到领取、补充、停止、结果、核对和回退路径 |
| agentprofile 数据画像 | 待使用证据决定 | 先明确消费方和历史分析指标，再决定迁移或合并 |
| bi 运营资源 | 待使用证据决定 | 先确定资源/成本口径，任务计数不冒充资源统计 |
| usage 历史用量 | 兼容保留 | 本次执行 token 保留；历史趋势、额度与混合运行时统计另验 |
