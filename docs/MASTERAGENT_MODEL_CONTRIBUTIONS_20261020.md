MasterAgent 的演进可概括为：**用户持续定义产品方向，Opus 协助建立并长期完善可用体系，Fable 推进实证审计和工程加固，Astra 在已有资产上完成 3.0 独立协调基座，并继续开发 3.1。** 这条主线存在交叠：Fable 出现以后 Opus 仍在参与，提交中还有 Sonnet 的明确贡献。用“主力变化、并行协作、逐步继承”描述，比三个模型依次完全接替更符合记录。

## 二、Opus：建立体系，并持续扩展协作能力

Opus 阶段最重要的贡献，是把“多个可以旁观、可以互相协助的会话”做成了实际系统。早期已具备角色注册、文件邮箱、领取与回填、事件唤醒、请求应答、审计、审批标记、恢复和 WebUI。这些能力形成了后续重构的需求基线；不能因为 3.0 使用了新实现，就把早期资产算作没有价值。依据：首提交 `a063a74`、[早期架构评审](ARCHITECTURE_REVIEW.md)。

7 月 BUS 2.0 的整理进一步将 `agentbus.py` 从文档所记的 3267 行拆成 175 行入口和 20 个内部模块，收敛状态判据、跨存储引用及命令入口，并维持既有调用。这个结果体现的是已运行系统的模块化与兼容维护，不是单纯增加功能数量。依据：`76da699`、[2.0 变更清单](BUS_2.0_CHANGELOG.md)。

Opus 之后仍参与通用探针、agent 数据画像和自我迭代宪章。9 月 16 日的宪章已将“业务与基建分离、协作保持在线”写成用户要求，并要求代表性验证和回退条件。9 月 23—24 日还有 Opus 署名的 UI 分离读方及上下文展示修改。因此，把 Opus 的角色缩减为“先搭一个粗糙原型”不公平。依据：`3e69ef2`、`5d5cc4d`、`21dadb7`、`1ffac70`、`2f3da99`。

这一时期也留下了与具体宿主、文件状态及业务环境耦合的负担。早期架构评审对领取排他的保证后来被实证纠正；部分状态和维护逻辑仍需要后续收敛。这说明初期工作主要在满足真实使用并扩展能力，不能据此推导 Opus 的普遍能力上限。

## 三、Fable：实证纠错、并发加固与业务分离

Fable 的贡献明显超过“优化了一些”。7 月 28 日的工程清单记录四路独立代码审查，覆盖核心架构、并发和崩溃一致性、进程以及 WebUI；清单最终记录 28 项完成。其主线包括领取互斥、共享 JSON 更新锁、原子写与临时文件冲突、超时进程树清理、任务归属、请求契约、审批守卫和稳定公共接口。清单是多角色共同完成，不能将其中全部 UI 工作也独占归给 Fable。依据：`5cb6d51`、`03f913e`、`75190b9`、[工程清单](BUS_EXCELLENCE_PUNCHLIST.md)。

一个很具体的改进案例是任务领取：

1. 6 月文档曾称当时使用 `os.replace` 的领取协议能保证只有一个成功者、不会重复执行。
2. 7 月 Fable 审查记录了本项目协议的双赢家问题，实际修改加入 `O_EXCL` 排他锁，文件搬运保留在锁内。
3. 历史清单记载了 120 轮、每轮 6 个进程的单赢家验证。

这可以支持“Fable 将早期依赖假设的保证加固成可验证机制”。它不意味着 `os.replace` 本身不原子，也不是跨模型能力排名。上述测试是当时的记录，本次历史整理没有重跑。依据：早期评审第 59、71 行，工程清单第 7、13—15 行，`03f913e` 的实际代码差异。

业务分离同样有明确的 Fable 贡献：7 月 29 日的角色注册分仓和业务名单派生，9 月的能力双表、业务注册表外迁、空载检查、通用资源锁和业务工具外迁，都发生在 Astra 3.0 重构之前。9 月 23 日的 Fable 5.1 框架审阅还将失联分型、通知消耗和剩余分离缺口联系起来，形成下一批改动依据。依据：`26ec7cb`、`f275fb2`、`72e61f4`、`6b689d3`、`54896fe`、[9 月框架审阅](FRAMEWORK_REVIEW_20260923.md)、[v2.14 分离记录](../fork_exchange/genesis_20260923_separation-biz-infra.md)。

这一轮分离主要改善注册表、读取路径、工具归属和通用机制，尚不能替代后来的业务包、部署配置、安装代次与执行状态边界。准确的评价是：**Fable 已经推进了平台化，并为 3.0 提供了实际基础；Astra 接手的仍是一套需要继续重构的系统。**

## 五、Astra：独立基座、事务语义与发行验收

Astra 阶段的主要变化，是将已有的分离方向推进到业务安装、部署绑定和执行归属边界：平台核心、业务包、部署配置和运行状态各有职责；任务与执行尝试分开；身份、安装、角色、代次和租约共同约束执行与发布。业务替换由“清走业务文件后还能启动”继续推进为“同一构建空载→A→B→恢复 A”，验证平台身份、业务上下文和持久状态的隔离；业务文件工具及操作系统权限隔离仍待后续独立验收。这条重构主线来自用户明确要求。[Astra 审阅](ASTRA_PLATFORM_REVIEW.md)第 7、15、65 行同时记录了用户要求与前期分离成果。

| 方面 | 已交付的主要贡献 | 验收或范围 |
| --- | --- | --- |
| 3.0 业务与部署边界 | 独立 `masteragent`、版本化业务契约、不可变安装快照、部署绑定与换域 | 公共契约接入合成业务，最终包完成真实 A→B→A |
| 3.0 协调状态 | SQLite 事务状态、Task/Attempt、执行所有权、持久决定、补充、结果与通知、显式迁移和待核对恢复 | 避免把“结果不明”处理成可安全自动重跑 |
| 3.0 Codex 执行 | 从单次文本执行推进至 App Server、常驻成员、双租约、事件接单、运行中纠偏、停止与进程退出核对 | 10 月 13 日正式版限 Windows 前台常驻、纯文本协作 |
| 3.1 工作台 | 统一查询、HTTP/CLI 共用公共命令、只读生命周期、草稿作用域、跨代任务历史及送达层次 | 使用合成数据完成浏览器和接口验证；完整旧功能迁移仍未完成 |
| 3.1 运行事实 | 请求模型、服务端报告与实际推理证据分开；用量来源与累计范围明确 | 未采集的实际模型保持未知，不能将原生报告当底层推理证明 |
| 3.1 存储与搬运 | 来源接纳与 Task 同事务、结果与投递意图同事务、目的端去重、原回执核对、受控 SourceStore、固定端点和独立常驻搬运 | 当前 schema 6；dev.4 为限定范围的合成验收，阶段 B 尚未整体完成 |
| 长期可维护性 | 后续 34 个工单、依赖与回退条件、继任入口、历史包和开发证据归档 | 规划及封存本身有交接价值，不能计作未来能力已经实现 |

3.0.0 最终包记录 10 个真实原生 Attempt、42 项检查通过；此前失败候选的 2 个 Attempt 单独保留，共 12 个实际 Attempt。其回归记录为 368 项运行、367 通过、1 项权限跳过。3.1 dev.4 记录为 648 项运行、646 通过、2 项权限跳过，另有前端 52 项通过；该批没有新增真实模型验收。这些是各构建的验证记录，不是可横向比较的模型质量分数。依据：[3.0 发行说明](MASTERAGENT_3_RELEASE.md)、[3.1 实施进度](MASTERAGENT_3_1_PROGRESS.md)、[dev.4 清单](../releases/3.1.0-dev.4/release-manifest.json)。

Astra 阶段也有需要保留的纠偏：最初五入口工作台与旧 UI 差异较大，用户提出疑问后才补齐 21 项入口迁移清单；目录齐全仍不等于功能全部迁入。3.0 专用目录的重复登录体验也留下了部署改进项。真实 Claude、混合团队、业务工具、原生审批、完整存储恢复和生产接管仍有未验范围。因此，Astra 的成绩应写为“完成有明确边界的 3.0 发行，并持续推进 3.1”，不能写成“已经统一所有能力”。

十月旧 bus 的 Codex 信使和宿主恢复线、运行负责人的接管准备，以及 MasterUI/MasterAgent 的审阅意见也贡献了成果。文档并未逐项提供这些会话的模型身份，故归为**十月协作成果、模型未单独归因**，不全部记作这个 Astra 开发会话的独立作品。

## 六、用户与共同经验的贡献

用户承担的贡献贯穿各阶段：选择“可见、可协作、运行中可纠偏”的产品形态；坚持业务可替换；决定 3.0 定位和 3.1 本机统一工作台；发现 UI 覆盖落差；要求跨模型接入、存储改进及未来可接续的规划。9 月宪章已直接保存用户对分离和在线的要求，10 月重构也继续由这些目标约束。

8 月 daemon 批量转换及回退，是值得保留的共同经验：单个角色能执行，不等于整个团队仍能低成本交流和接受纠偏。项目随后将代表性试点、系统层验证和回退条件纳入治理。这段教训有联合复盘支持，但不能仅按日期把全部决策或错误归给某个模型。依据：[联合复盘](POSTMORTEM_daemon_direction_error.md)、[自我迭代宪章](SELF_REDESIGN_CHARTER.md)。

未来开源介绍适合采用“用户主导、多个模型辅助、角色分工与独立验证”的叙事。只列模型而省略用户与协作流程，会遗漏决定产品方向和发现偏差的重要来源。
