# MasterAgent 后续版本路线与本机封包规则

更新：2026-10-20。当前正式版为 `3.0.0`；当前已验开发版为 `3.1.0-dev.4` 首批，schema 6、公共 API `3.1-dev1`，B 尚未整体完成。本文件把已采纳的 A → B → C → D 顺序对应到后续包号，不改变 [3.1 方案](MASTERAGENT_3_1_PLAN.md)、[审阅取舍](ASTRA_3_1_REVIEW_DECISIONS_20261019.md) 和 [UI 覆盖清单](MASTERAGENT_3_1_UI_COVERAGE.md) 的承诺。实际证据以 [实施进度](MASTERAGENT_3_1_PROGRESS.md) 为准。

未来版本先规划、实现、验收，再生成对应二进制。日期不替代门槛，开发包不提前标成正式版；源码归档、部署和旧服务切换分别执行。

后续会话先读 [接手入口](MASTERAGENT_NEXT_SESSION.md)，按 [逐项执行工单](MASTERAGENT_EXECUTION_BACKLOG.md) 的前置、最小产物、测试和证据逐步实施。本路线负责版本范围，工单负责可复现执行；任何一项的计划说明都不等于已验实现。

## 始终保留的目标

- 业务可任意更换：同一构建完成空载 → 业务 A → 业务 B → 恢复 A。角色、知识和流程来自业务包，运行目录与权限来自部署；基座不增加具体业务或角色名分支。
- 一个本机 Web 工作台串起业务、团队、任务、结果、资料和运行设置。页面与执行服务分离，查看页面不启动维护、迁移或执行。
- Codex 与 Claude Code 共用协调契约，各自保留原生语义；账户连接、角色部署、平台任务和原生历史分层。未验证的能力显示具体原因，不冒充在线或已支持。
- 每个独立状态根以 SQLite 为协调权威，加显式本机制品目录；UI、CLI、兼容适配使用同一领域命令。数据、验收与发行包默认留本机。
- 执行期间能接收补充、协作和停止；不确定执行与投递保留核对责任，不靠重跑模型补回执。

## 版本与放行顺序

以下判断需保留理由。重新评估要有可复现证据与独立方案，不因接手模型变化重新猜一遍。

| 判断 | 当前理由 | 何时重新评估 |
| --- | --- | --- |
| 每部署 SQLite 事务权威 | 任务/归属/结果/投递意图可在同一事务裁决；换数据库不能替代所有权协议 | 实测容量、锁等待或明确多机部署需求超过已验边界，再比较迁移成本；不默认引入服务或 WAL |
| 共同契约、两种原生适配 | 用户工作流统一，Codex/Claude 的原生事件、权限和恢复语义不同 | 固定原生版本能力变化时按契约重新测试；不机械互译参数或拼接未知状态 |
| 业务与部署分层 | 业务可换，目录/账户/权限属于运行环境；同构建 A→B→A 可直接验证 | 新业务确实无法通过公开契约表达时，扩通用契约并补跨业务测试，不能增加业务名分支 |
| 等待期间继续收信和停止 | 用户需要纠偏；阻塞审批或协作不能令执行失去控制 | 若运行时缺少此能力，明确受限或停止接入；有实际新协议后独立适配，不删掉需求 |
| held 先核对、不重跑 | 不明不等于未执行，重跑可能重复副作用或产生另一结果 | 只有原对象的权威证据及明确重试决定才推进；不能用超时、空目录或新 ID 证明安全 |

| 版本 | 状态与交付范围 | 必须具备的放行证据 |
| --- | --- | --- |

| `3.1.0-dev.1`～`dev.2.2` | 已交付的工作台、公共操作、运行事实与阶段 A | 保留各包独立证据及已知限制，不以新测试追认旧构建 |
| `3.1.0-dev.3` | 已交付 B 的持久路由、本机参考目的端、回执显示和 schema 5 迁移核心 | 当前合成验收有效；旧入口接入、常驻搬运和真实文本仍未完成 |
| `3.1.0-dev.4` 及后续修订 | B 收尾目标保留；首批已交付受控来源、端点绑定及常驻搬运，完整核对工作台与真实试点未完成 | B 放行仍要求全部参与入口签收、异常管理、单角色→预编排双角色真实 Codex；首批开发包不代表放行 |

| `3.1.0-rc.N` | 候选版：冻结实际能力，收齐 UI 去向、连接/恢复体验、操作手册、迁移和降级清单 | 完成下述正式版清单；未达门槛继续 rc 或开发版，不通过改名称绕过 |
| `3.1.0` | 仅对验收通过且明确声明的范围正式发行 | 完成发行复核；记录未开放能力与兼容去向。仍不等于旧 fleet 自动切换 |
| `3.1.x` | 已发布范围内的缺陷修复、兼容与运维体验改进 | 复现、修复、针对性回归和原关键闭环验证；不以补丁包偷偷扩大工具或数据权限 |

包号对应交付目标，不预占数据库版本。增加持久结构时使用当时下一实际 schema，并提供显式备份迁移；兼容的公开附加字段继续按能力协商，改变既有语义才升 API。任一批次可拆 `dev.N.1` 等修复包，必须保留各构建自己的摘要与验收结果。

## dev.4：先收齐 B 的真实入口闭环

依据 [领取入口清单](MASTERAGENT_3_1_ROUTING_ENTRYPOINTS.md)，先固定参与试点的来源、消费者、目的端和负责方。来源生产、领取、完成、恢复及旁路入口全部有清单；未适配来源明确留旧线，不将核心的 legacy lane 当成旧 bus 已遵守的排他规则。

交付自动搬运的独立启动、停止、状态和恢复入口，保持源搬运、执行、结果发送三类租约独立。事件唤醒后查持久状态；重启从账本继续，不扫描私人会话或新造投递 ID。held 进入可见核对清单，只有原目的端 root + instance 的持久证据能解除不明状态，核对操作与结果发送有明确审计。

验收先用合成入口验证旧/新消费者竞争、重复/迟到消息、各事务间崩溃点、回执丢失、长正文完整性、冻结和回退。再在本次单独明确认证范围的独立环境运行虚构文本：单角色验证保存、领取、运行中补充、停止、结果投递和不明状态；双角色由平台预编排，核对父子归属和完整结果，不宣称模型自主派活。

通过门槛是所有参与入口都受裁决，并能逐条追溯来源 → admission → task/attempt → result → delivery/receipt。真实模型未运行时可交付适配开发包，但 B 仍标未完成。当前 3.0 验收认证复用授权不延伸到本次试点。

## dev.5：让存储和观察可恢复

事件与领域变更同事务提交，提供有作用域的持久游标、分页和断线续读。游标失效时明确要求重新读取快照；watcher 只负责唤醒，不能充当事件记录。输入与指令来源、任务链和结果按业务、角色、代次、执行归属查询。

制品经历暂存、校验、登记、ready 和异常核对，保存归属、相对位置、字节数和摘要。文件与数据库并非跨资源事务，分别验证封存前后崩溃、孤立文件、缺失和内容变化；未经核对不自动删除。大正文继续遵守目的端限额，不能以新索引为由放宽或静默截断。

备份分别覆盖平台发行、协调状态和业务资料，认证及原生私人历史不进入通用包。恢复到独立目录，核对任务、未决输入、投递阶段、目的端绑定及制品摘要。先测事务/查询/锁等待，再决定是否需要改变存储模式，不默认开启 WAL、Redis 或数据库服务。

## dev.6：按能力开放工具和原生协作

遵守 [原生审批契约](MASTERAGENT_3_1_NATIVE_APPROVAL_CONTRACT.md)。工具权限取业务声明、角色部署、平台策略与实际隔离能力的交集；策略及完整请求内容在批准前固定。先评估有限单次 `file_change`，再评估 `command`，两者都必须有允许与越界行为证据；未通过继续拒绝。

RuntimeApproval 与平台 Decision 分开持久化和展示。精确绑定运行时、安装、角色、代次、Attempt 与原生请求；验证重复/迟到答复、发送前后停止、已写但未确认、原生关闭与工具终态。等待用户或其他 agent 时继续接收补充和停止，不持有数据库事务等待。

原生协作桥单独定义授权、父子归属、等待/继续执行及取消语义。dev.4 的预编排双角色成功不能算作此桥已完成。工具、原生恢复和认证连接复用也各有独立能力与真实证据，不捆成一个“深度接入已完成”。

Claude 按共同契约实现独立适配和替身测试，环境恢复后先验 Claude 单独闭环，再验 Codex/Claude 工作态交接。两种原生会话不互相 resume。Claude 不可用不阻塞前述公共实现和 Codex 试点，但真实 Claude/混合团队缺口持续保留在 3.1 放行表。

## 候选版与正式版清单

每个候选包保存一份带证据链接的放行表。必需项未通过，保持开发/候选状态；确需带已知限制发行时，先把具体受限能力、替代入口及用户影响列为范围决定，不能自行取消或挪至 3.2。

1. 同一最终构建通过空载 → A → B → A，跨业务、角色、代次、执行及目的端隔离；公开契约可接不同业务，无具体业务分支。
2. B 的参与入口、常驻搬运和真实文本闭环完成；C 的事件、制品与恢复证据齐全；D 对声明开放的每项工具、审批与协作能力单独通过。源码静态核查、替身和真实运行分别标记。
3. 工作台日常路径完成浏览器验收：提交、交接、补充、决定/审批分名、停止、完整成果、回执、核对、历史与资料。缺失/离线/截断状态明确，刷新与切换保留或隔离正确的草稿和选择。
4. 21 个旧入口逐项列出原生实现、兼容入口、未完成及消费方；二级功能和跨页交互一起核对。兼容深链在新版、旧版、离线状态分别验证；没有等价承接或明确范围决定的能力不退役，不用目录数量算覆盖率。
5. 连接、角色部署、原生历史、平台接续各自说明。Claude 真实结果未取得时明确未验；不得宣布混合团队通过。若拟发行 Codex 已验范围，须形成明确的受限发行决定，Claude 的 3.1 承诺仍单列追踪。
6. 旧程序拒绝新库、迁移备份、活动任务阻断、迁移失败回滚、独立目录恢复和回退核对通过。回退不把新任务搬回旧 inbox，不覆盖新账本；已接纳工作保留原归属。
7. 最终包、源码/资源、测试、文档、证据与 manifest 对齐；操作手册写清默认只读、启用写入口、执行服务、冻结、核对和恢复方式。消费方接入另有范围与在飞工作清单，封包不会自动切服务。

## 3.1.x 与 3.2 的边界

3.1.x 优先处理正式范围内的缺陷、升级兼容、已声明能力的可靠性与可用性；涉及新结构时仍显式迁移。安全边界与数据范围变化不能因版本号是补丁而省略验证。

3.2 的候选方向是基于实际使用证据增强跨任务组织、任务线/工作组、长期任务、历史成本与资源分析、可选扩展和更复杂部署。这里只是建议，不表示当前已有多机写入、任意原生历史恢复或完整语音集成。每项先核对 3.1 去向：若属于未完成承诺，继续列在 3.1；只有已明确兼容保留后的新增能力或独立立项范围，才进入 3.2。

## 封包、归档与副本清理

本项目的版本归档统一放在 `C:/apphome/agent_fleet/releases/`，每个已交付版本一个目录。历史文档中的会话路径作为原始证据位置保留，迁移清单另记录新位置；未来文档引用优先使用项目内归档。

每版归档至少包含：

- `manifest`：包号、发行/开发状态、schema/API、各文件相对路径、大小和 SHA256、封包时间及证据索引。
- 已验二进制、对应源码与静态资源；测试、构建脚本和文档快照注明采集时间及来源。历史源码若只能从旧包恢复，明确恢复范围；当前测试/文档不能伪装成旧版当时快照。
- 验收结果与限制：合成/替身/真实运行的分界、跳过项、已知未完成能力、迁移和回退说明。只收本轮授权的最小本机证据，不收认证、私人会话或生产状态。

归档按已验字节复制，不以当前源码重建同名历史包；已验归档不覆盖，修复生成新版本。源/测试/文档快照是交付留档，不替代在线状态和业务资料备份。尚未实现的 dev.4 及以后只保留本路线和待办，不生成占位二进制或虚构验收 manifest。

项目外副本清理顺序为：限定属于本项目的已知路径 → 复制到项目内 → 逐文件核对数量、字节数及 SHA256 → 更新引用和依赖路径 → 处理仍使用旧路径的专用预览 → 删除核对通过的源副本 → 留清理记录。唯一数据、运行中状态、未知归属目录、链接目标和认证目录不按“副本”推断删除。清理专用合成预览不代表授权停止或迁移旧 fleet/生产服务，运行态须按各自职责单独处理。
