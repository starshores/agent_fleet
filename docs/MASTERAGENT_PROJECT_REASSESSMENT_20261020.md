# MasterAgent 项目整体重新评估

评估日期：2026-10-20。对象是整个项目及其原定目标，覆盖旧协作线、V3 基座、3.1 工作台、运行时、存储、迁移和交付。模型贡献属于项目历史背景，另见[模型贡献材料](MASTERAGENT_MODEL_CONTRIBUTIONS_REASSESSMENT_20261020.md)，不作为本报告的评分依据。

本报告是分析交付，未修改产品实现、启动生产服务、切换队列或发布新版本。建议尚未冒充已实施工单。评估基线、文件摘要和复现证据保存在[本轮证据目录](history/project-reassessment-20261020/README.md)。

## 1. 整体判断

**项目方向成立，V3 的协调核心值得保留；当前已经有具备较完整协调守卫和限定故障验收的新基座，但尚未形成能够完整承接旧团队工作方式的统一产品。3.0 的限定范围发行成立，不能据此推导 3.1 已接近整体收尾。**

工程进展主要体现在身份、业务代次、执行归属、事务、回执和故障恢复边界。用户目标则要求：一次明确部署后，从网页发起工作，看清谁在处理，执行中补充或停止，收到可确认的成果，出现中断仍能核对并继续。这条路径的若干环节尚未接通。下一阶段的主线应从“增加可靠组件”转为“让这些组件共同完成一段真实工作”。

最重要的三个判断：

1. **业务分离已取得实质进展，业务任意替换还需扩大证据。** 不可变业务包、部署绑定和 A→B→A 已验证；工具业务、不同工作流和低成本切换尚未一起证明。
2. **一体化的主要缺口是生命周期和恢复的一致性。** 把界面放在一起、把更多数据装进一个库，都不能替代连接、执行、交付、异常核对及恢复之间的共同规则。
3. **新旧线需要按工作流迁移。** 新基座显式约束协调归属和事务一致性，旧线仍保留原生续接、工具、长期角色工作态及运维功能。新线目前不是旧线能力的严格超集，本轮也未做新旧线同一故障矩阵的质量比较。

不建议推倒重写、先换数据库或一次重做全部旧页面。建议保留 A→B→C→D 的依赖结构，在下一批交付中补齐本文发现的正确性缺口，把少量 C 的观察与恢复能力提前服务于 B 的试点；未完成的 3.1 范围继续保留，不能暗移到 3.2。

### 对“业务任意换”的重新解释

不能把“任意”理解为无需能力约束即可运行所有业务。应要求：在公开能力契约覆盖的范围内，更换业务只改业务包和部署配置；缺少通用能力时，明确扩展契约，不在核心添加具体业务或角色名判断。

下一次验收应选两个在输入、产物、协作和权限需求上明显不同的合成业务模型。例如，一个是纯文本审阅并返回文字意见，另一个是多角色数据处理并形成受控文件成果。后者的真实工具执行必须等待 D 的隔离门槛；现在可先用替身验证契约缺口。记录每次切换需要的人工步骤、认证次数、保留的工作态和必须重新批准的事项，不能只证明角色名称和任务正文换了。

## 5. 应保留什么，真正要改什么

| 决策 | 原因 | 应补的部分 |
| --- | --- | --- |
| 保留业务包、部署和执行身份分层 | 避免角色名、宿主路径、模型选择写入业务无关核心；已有 A→B→A 与越界拒绝证据 | 双业务差异化验收；双向路径占用守卫；连接与工作态切换成本 |
| 保留 claim→事务外执行→complete 和多级租约 | 外部模型不能参与数据库事务；进程、成员、Attempt 的事实不同 | 两执行入口输入一致；未来工具资源接管 |
| 保留不明结果待核对、不自动重跑 | 回执丢失可能已执行/送达，重跑会增加副作用 | 让用户找得到、看得懂并可完成核对，覆盖浏览器重载 |
| 保留每部署 SQLite 和来源/目的端各自权威 | 本机模式尚无证据需要外部数据库服务；不存在可凭文档声明的跨库原子事务 | 有界查询、备份范围、三库对账、制品封存与恢复 |
| 保留只读查询和执行服务独立生命周期 | 打开页面不应隐式启动模型；观察不应改变证据 | 显式部署流程、就绪诊断、可解释下一步 |
| 保留不同原生运行时的能力差异 | 取消、审批、恢复不能通过参数翻译伪造一致 | 最小运行接口和能力矩阵；Claude 独立原生验收 |
| 保留兼容线直到工作流被接住 | 旧线拥有新线暂缺的产品能力 | 按“来源＋消费者＋恢复器＋用户操作”逐项灰度，不按角色数宣告接管 |

替代路线也需说明：只在旧线增加统一 UI，能更快改善眼前操作，但会继续承受旧身份、存储和业务耦合，不能完成用户强调的基座分离；重写为另一套框架或更换数据库则会重新付出正确性与迁移成本，目前没有证据支持。推荐沿用新基座并分批连接旧消费场景。

项目复杂度并非都应删除。身份、代次、原生执行、投递、处理、用户已读表达不同事实，盲目合并会损失恢复能力。可以减少的是重复“当前版本”描述、入口间重复输入构造、未被第二种运行时证明的抽象，以及没有用户场景约束的后续扩展。

## 7. UI、持续协作与存储应怎样共同验收

**主验收场景：** 新使用者按说明完成一次明确部署，从网页发起任务，看到正确执行者；在执行中补充要求，看到补充的实际接收状态；必要时停止并分辨“已请求”和“已退出”；收到完整成果；故意制造一次回执丢失或进程中断后，能在首页找到问题并按原 ID 核对，没有重复执行。

分别验证页面自取成果与外部来源回送。对于双角色场景，除了两个角色都有结果，还需证明父执行实际收到了子结果，且其来源、内容与代次正确。对于将来的自主协作，还需另验“执行中请求帮助→保持可补充和可停止→收到结果→继续工作”；预编排不代替它。

旧 UI 按使用目标验收，而非按页面数量：

- 日常任务闭环先原生完成：提交、接单、补充、决定、停止、成果、异常核对。
- 运维诊断可保留兼容：上下文、信使/自醒、角色生命周期、历史用量、提示词检查，但具体版本、深链和离线行为要验证。
- TODO、工作组、任务线、长程图和语音保留独立语义，按实际使用证据安排；不因为它们不像 V3 Task 就默认退役。

存储一体化的验收应回答每项数据“谁负责、属于哪个业务/任务、怎样引用、怎样恢复”。核心库、来源库、回执库、文件制品、原生历史可以分开存放，但必须有统一归属视图和明确备份边界。源码归档、状态备份、业务资料与原生秘密是不同交付物；当前静态封包不能作为运行态恢复证明。

## 8. 后续投入与维护方法

额度充裕可以支持交叉审查和故障复现，但当前主要瓶颈是集成证据与人工使用成本。建议同时推进一条主交付流程和一项独立风险研究，避免平行扩大多个用户尚不可用的系统。每个后续会话只需获得当前事实、一个具体工单、最小复现、验收与回退边界，无需重新推理全部历史。

下一次真实试点应记录以下指标，作为后续决策依据；本轮没有采集这些数值：

| 指标 | 用途 |
| --- | --- |
| 首次部署与 A→B→A 的步骤数、人工耗时、登录次数 | 判断业务替换与连接整合是否真正降低使用成本 |
| 任务保存→被接单→首个可见进展→成果可见/收到的时间 | 找出调度、执行、投递、UI 的实际瓶颈 |
| 重复执行数、遗漏正文/错误归属数 | 作为故障注入后的硬性正确性门槛 |
| 不明执行与 held 的数量、最长未核对时间、人工处置步骤 | 判断恢复机制能否被实际操作者完成 |
| 恢复前后任务、回执和制品的逐项对账差异 | 判断备份是否可用，而不只判断备份文件存在 |
| 每种真实业务的成果质量、人工修订量和已知来源用量 | 判断多角色协作是否值得其复杂度；不把模型报告或 token 数当质量 |

建议把构建元数据作为版本/schema/API 的事实源；接手入口只保留当下摘要，进度文档保留按日期的证据，工单保留未完成责任。未来开源材料沿用本报告的证据层次，清楚区分“实现”“合成通过”“历史真实通过”“当前现场未知”。模型贡献分析作为起源说明使用，不能代替项目质量与产品完成度的证明。
